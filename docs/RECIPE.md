# What we reproduce, and what we can't

Everything here is grounded in the MedGemma Technical Report ([arXiv:2507.05201](https://arxiv.org/abs/2507.05201)).
Quotes are verbatim. Read this before interpreting any result from this repo.

## The finding that shapes the whole project

MedGemma's medical **text** ability does not come from pretraining on a secret
medical corpus. Two direct quotes:

> "The MedGemma 4B multimodal model utilized all of the following steps while the
> text-only version of MedGemma 27B leveraged the post-training stage alone."

> "Notably, we did not introduce further medical text-only data in this step, as
> the original Gemma 3 mixture was already general-purpose and large-scale."

So MedGemma-27B-text — the model with the headline MedQA jump of 74.9 → 87.7 —
is Gemma 3 27B plus **post-training only**. An SFT-only reproduction of the text
recipe is therefore faithful *in kind*. That is the good news.

## The three things we cannot reproduce

1. **The teacher's logits.** Post-training adds "medical text data generated by a
   large IT teacher model," sampling **responses *and logits***. No public API
   exposes logits, so we cannot replicate the distillation objective — only
   response-level SFT on public chain-of-thought. **This is the single biggest
   fidelity gap** and the main reason our numbers should not be expected to land
   on MedGemma's.
2. **The 200k synthetic questions.** Never released. We substitute public
   reasoning corpora (ReasonMed, medical-o1, MedReason).
3. **HealthSearchQA answers.** Table 1 lists 3,375 rows, but every public release
   is *questions only, no reference answers* (and the counts conflict: 3,173 in
   the Med-PaLM release vs ~4,576 on the hub). Unusable for SFT; registered
   `eval_only` in `gemma_med/mixture.py`.

MedGemma's RL stage is also out of scope for now — the report says "all
multimodal post-training was performed via RL," but our text-only scope makes
SFT the reasonable first target.

## Base checkpoint: why `-it`, not `-pt`

MedGemma starts from Gemma 3 **`-pt`** and applies Google's *entire* post-training
recipe (distillation + RL, "the same as in Gemma 3 development") with medical
data folded in. We have the `-pt` checkpoints but not that recipe.

SFT-ing `-pt` on medical QA alone produces a model that answers MedQA but has no
general instruction-following — not comparable to MedGemma. Starting from `-it`
approximates "Gemma 3 post-training already applied, now add medical," which is
much closer to what MedGemma actually is, and yields a clean three-way
comparison: `gemma-3-*-it` (baseline) → ours → published MedGemma.

The `-pt` checkpoints ship **no chat template**; `gemma_med/chat.py` supplies one
verified byte-identical to the official `gemma-3-1b-it` template (`tests/test_chat.py`).

## Hyperparameters: ours, not theirs

The report gives **no hyperparameters** for the main post-training run — no LR,
batch size, or step count. The only published numbers (LR ∈ {1e-7, 5e-7, 1e-6},
1 epoch, full-parameter, "cross-entropy on completion only") are from §5's
*downstream* fine-tuning experiments — adapting an already-tuned MedGemma to a
narrow task. Using those LRs for our stage underfits badly.

We therefore use conventional Gemma 3 SFT defaults (1e-5, cosine, 2 epochs,
effective batch ≈128) and sweep LR at 1b. **These are our choices; do not report
them as MedGemma's.** The one thing we do carry over is completion-only loss.

## Data mixture

`gemma_med/mixture.py`. Table 1's text sources, all public:

| Source | Table 1 N | Ours | Note |
|---|---|---|---|
| MedMCQA | 182,806 | ~182.8k | matches |
| MedQA | 9,275 | ~10.2k | paper filtered ~9% by an unstated method; we can't match it |
| AfriMed-QA | 1,003 | — | **gated on the hub**, needs an access request |
| MedExpQA | 434 | 434 | exact |
| PubMedQA | 1,000 | 500 | see below |
| LiveQA | 634 | 635 | ~exact |
| HealthSearchQA | 3,375 | 0 | questions only → eval-only |
| Synthetic | 200,000 | proxy | ReasonMed / medical-o1 / MedReason |

**PubMedQA, 1,000 vs our 500.** PubMedQA is both a training source *and* a
benchmark, and the hub ships `pqa_labeled` as a single 1,000-row split. The
official benchmark test set is 500 of those 1,000. Table 1's "1,000" therefore
implies MedGemma trained on its own PubMedQA test split, which would inflate
their PubMedQA number. We hold out the official 500 by `pubid`
(`gemma_med/data.py:pubmedqa_test_ids`) and train on the rest. Our PubMedQA
result is comparable to the literature; theirs may not be.

**Decontamination is mandatory.** MedReason and ReasonMed are *built from*
MedQA/MedMCQA — MedReason even carries the provenance in a `dataset_name`
column. Blending naively leaks eval questions into training. `build_mixture`
drops any row whose normalized question matches a MedQA-test or
MedMCQA-validation question, then dedups across sources (earlier sources win, so
Table 1 data outranks the corpora derived from it). `--no-decontaminate` exists
for ablations only; results from it are inflated by construction.

**medical-o1 sizing.** The `en` config is 19,704 rows, not the ~90k sometimes
quoted (that counts en/zh/en_mix/zh_mix together).


Three things worth knowing, all measured rather than assumed:

* **ReasonMed is ~85% redundant.** 940,536 of its 1,111,555 rows duplicate
  questions already present in MedQA/MedMCQA/MedReason. Only ~171k are novel (we
  cap at 80k). Treating its 1.1M headline size as 1.1M of *new* signal would be
  a mistake.
* **MedReason loses 62%** to the same effect — it is largely MedMCQA re-reasoned.
* **MedMCQA contains ~31k internal duplicate questions** (~17% of its train
  split). That's the dataset's own redundancy, not eval leakage.

Actual eval contamination was small (13 rows in MedMCQA, 2 in MedReason) — the
decontamination pass mostly buys us *deduplication*. But the leakage was real and
non-zero, and you cannot know that without running the check.

**LiveQA, 634 vs our 420.** LiveQA pairs multiple answers with the same question;
the paper's 634 counts pairs, our dedup keeps one row per question. If matching
Table 1 exactly matters more than dedup here, relax it for this source.

## Targets

MedGemma vs base Gemma 3 (report, Table 4). Our runs start from `-it`, so the
Gemma 3 column is the baseline to beat and MedGemma is the ceiling.

| Benchmark | Gemma 3 4B | MedGemma 4B | Gemma 3 27B | MedGemma 27B |
|---|---|---|---|---|
| MedQA (4-op) | 50.7 | 64.4 | 74.9 | **87.7** |
| MedMCQA | 45.4 | 55.7 | 62.6 | 74.2 |
| PubMedQA | 68.4 | 73.4 | 73.4 | 76.8 |
| MMLU Med | 67.2 | 70.0 | 83.3 | 87.0 |

**Expect an alignment tax.** The report measures it: MMLU Pro 43.6 → 39.1 (4B)
and 67.5 → 60.2 (27B). Our `default` mixture includes general-instruction replay
(`HPAI-BSC/Aloe-Beta-General-Collection`) to push back on this; the `paper_only`
mixture omits it, which makes the two a natural ablation.
